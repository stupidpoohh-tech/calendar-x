# Dada Calendar — 이관 전 진단 및 상용화 설계안

작성일: 2026-08-20
대상: `My_Calendar.zip` (CDN React + Babel standalone, 14파일 3,678행)

---

## 0. 요약

현재 코드는 **개인 1인용으로는 잘 작동하지만, 상용 서비스의 전제 조건 몇 가지가 구조적으로 빠져 있습니다.**
그리고 이 프로젝트가 내세우는 컨셉인 "같은 캘린더 축에서 3가지 관리"는 **아직 구조에 반영되어 있지 않습니다.**
탭 3개는 서로 완전히 격리된 3개의 캘린더이고, 축을 넘나드는 경로가 없습니다.

판단 3가지:

1. **MIGRATION.md의 절차(Vite 전환 → Cloudflare Pages)는 그대로 유효합니다.** 다만 그 전에 고쳐야 할 확인된 결함이 10건 있습니다. 그중 3건은 사용자가 기능이 동작한다고 믿는데 실제로는 저장되지 않는 종류입니다.
2. **골격 수정은 필요합니다.** 다만 "3탭을 없애자"가 아니라 "3탭을 하나의 타임라인 위의 3개 렌즈로 재정의하고, 네 번째 통합 렌즈를 추가하자"는 방향입니다. 축 간 전환과 현금흐름 예측이 붙는 순간 이 앱은 대체재가 거의 없어집니다.
3. **Supabase 이관은 지금도 권하지 않습니다.** 단, MIGRATION.md의 근거("동작 중인 앱을 옮기는 비용")와는 다른 이유입니다. 이관과 스키마 재설계를 동시에 하면 실패 지점이 두 배가 되기 때문입니다. Firestore를 유지하되 스키마는 새로 짜고 마이그레이션 스크립트로 옮기는 편이 안전합니다.

## 1. 현재 구조

### 스택

| 항목 | 현재 |
|------|------|
| 빌드 | 없음. `@babel/standalone`이 브라우저에서 JSX를 매번 트랜스파일 |
| 모듈 | 없음. `window.XXX = XXX` 전역 노출, `index.html` 하단 script 순서에 의존 |
| React | 18.3.1 `react.**development**.js` (프로덕션 빌드가 아님) |
| 인증 | Firebase Auth 이메일/비밀번호 |
| DB | Firestore `users/{uid}/items` 단일 컬렉션, 단일 스키마 |
| 배포 | 미연결 (Cloudflare Pages 예정) |
| 테스트 / 타입 / 린트 | 없음 |

### 화면

- **탭 3개**: `todo` (할 일) / `day` (💡 아이디어) / `money` (가계부)
- **뷰 2종**: 월간 캘린더(주 단위 레인 배치, 항목을 숨기지 않고 개수에 따라 바 높이 압축) / 월 필터 리스트
- **탭 상단 섹션**: `todo`·`day`는 고정 메모, `money`는 잔고 카드 + 대출 카드
- **모달**: 항목 생성·편집, 날짜/월 빠른 이동, 날짜 상세 시트, 설정 시트

### 데이터 모델

모든 것이 `items` 한 컬렉션에 들어갑니다. 특수 데이터는 `title`을 `'::balance::'`, `'::loans::'`로 표시하고
값을 `memo` 필드에 문자열/JSON으로 담는 우회를 씁니다. CLAUDE.md에 기록된 대로,
Firestore 보안 규칙이 필드 화이트리스트를 강제하고 있어 비표준 필드가 조용히 거부되기 때문입니다.

## 2. 확인된 결함

파일과 행을 직접 확인한 것만 적었습니다.

### F-01 · 치명 · 디자인 토큰의 절반이 CSS 파싱 단계에서 폐기됨

`index.html:61` 에서 `[data-theme="dark"]{...}` 블록이 닫힌 뒤,
`--c-red` ~ `--c-pink`, `--radius`, `--radius-sm`, `--radius-lg`, `--shadow-1~3`, `--font` 선언이
**어떤 선택자에도 속하지 않은 채** 62~81행에 남아 있습니다. CSS 파서가 이 블록을 통째로 버립니다.

결과:
- `body { font-family: var(--font) }` 가 무효가 됩니다. Pretendard를 CDN에서 로드하지만 **실제로는 브라우저 기본 폰트로 렌더링되고 있습니다.**
- 모든 `border-radius: var(--radius)` → 무시 (모서리가 각짐)
- 모든 `box-shadow: var(--shadow-1~3)` → 무시 (모달·카드 그림자 없음)

즉 지금 보고 있는 화면은 의도한 디자인이 아닙니다. 닫는 중괄호 하나 위치 문제이고, 고치면 앱 인상이 눈에 띄게 달라집니다.

### F-02 · 치명 · TODO 순서 변경이 저장되지 않음

`src/app.jsx:133-155` `reorderTodo`는 `setData`로 로컬 상태만 갱신하고 Firestore에 쓰지 않습니다.
로그인 상태에서는 `onSnapshot`이 다음 스냅샷으로 로컬 변경을 덮어쓰므로, 드래그로 정렬해도 새로고침하면 원위치합니다.

### F-03 · 치명 · 백업/복원이 Firestore를 보지 않음

`src/store.jsx` `exportJSON()`은 `loadData()`(localStorage)를 읽습니다.
로그인 사용자의 데이터는 Firestore에 있으므로 **백업 파일에 항목이 0개로 나옵니다.**
`importJSONText()`도 localStorage에 쓰고 `setData`로 화면만 바꾸므로, 다음 스냅샷에서 사라집니다.
"JSON 백업 내려받기"는 설정 메뉴에서 가장 눈에 띄는 항목인데 실제로는 동작하지 않습니다.

### F-04 · 높음 · 반복 일정이 저장만 되고 전개되지 않음

`src/item-modal.jsx:289`에서 `repeat`(매일/매주/매월)를 입력받아 저장하지만,
`calendar-view.jsx`·`list-view.jsx` 어디에도 `repeat`를 읽는 코드가 없습니다.
사용자에게는 동작하는 기능처럼 보이지만 반복 항목은 첫 날짜에만 나타납니다.

### F-05 · 높음 · 잔고·대출의 저장 방식이 다중 기기에서 깨짐

`src/money-section.jsx` — 대출 목록 **전체**가 단일 문서의 `memo` 필드에 JSON 배열로 들어갑니다.
두 기기에서 각각 다른 대출을 편집하면 나중 쓰기가 앞선 편집을 통째로 덮어씁니다.
잔고도 `memo`에 문자열로 들어가므로 집계·쿼리·히스토리가 불가능합니다.
이 우회는 Firestore 규칙 때문에 생겼는데, **규칙이 레포에 없어서 지금은 그 내용을 확인할 방법이 없습니다.**

### F-06 · 높음 · 전 항목 무제한 구독 (상용화 원가 구조)

`src/app.jsx:31-40` — `users/{uid}/items` 전체를 `onSnapshot`으로 구독합니다.
1인 사용에서는 문제가 없지만, 3년치가 쌓인 사용자가 앱을 열 때마다 전량이 전송되고
Firestore 읽기 과금이 (사용자 수 × 보유 항목 수)로 선형 증가합니다. 월 범위 쿼리로 바꿔야 합니다.

### F-07 · 높음 · 비밀번호 재설정 경로가 없음

`src/lock.jsx`는 `signIn` / `signUp`만 구현합니다.
**비밀번호를 잊으면 데이터에 영구히 접근할 수 없습니다.** 이메일 인증도 없어 오타 가입 시 복구 수단이 없습니다.
1인용이면 감당할 수 있지만, 남의 데이터를 받는 순간 이건 사고입니다.

### F-08 · 중간 · 낙관적 업데이트 부재 + 오프라인 미지원

`src/app.jsx:87-99` `saveItem`은 로그인 상태에서 `setDoc`만 호출하고 로컬 상태를 갱신하지 않습니다.
Firestore 왕복을 기다리는 동안 입력이 반영되지 않고, 오프라인 지속성도 켜지 않아 지하철에서 앱이 멈춥니다.
(CLAUDE.md의 "낙관적 업데이트" 항목은 localStorage 시절 이야기이고, Firebase 경로에는 적용되지 않았습니다.)

### F-09 · 중간 · Tweaks 패널이 상용 번들에 섞여 있음

`tweaks-panel.jsx`는 568행으로 **전체 코드의 15%**입니다.
Claude Artifacts 호스트와 `postMessage`로 통신하는 프로토타이핑 도구이며 상용 빌드에 들어가면 안 됩니다.
게다가 여기서 조정하는 `weekStart`·`compactCalendar`는 `MonthCalendar`에 전달되지 않아
(`calendar-view.jsx`의 `WEEKDAYS_MON`이 상수 고정) **바꿔도 아무 일도 일어나지 않습니다.**

### F-10 · 낮음 · 확인창이 `confirm()` / `alert()`

`src/app.jsx:126`, `179-186`. 브라우저 기본 대화상자는 모바일에서 도메인명이 노출되고 스타일링이 불가능합니다.

### 그 외 (구조적)

- **타임존 없음.** 날짜가 `YYYY-MM-DD` / `YYYY-MM-DDTHH:mm` 문자열이고 로컬 `Date` 기준입니다. 다기기·해외 사용자·알림이 들어오면 깨집니다.
- **국제화 없음.** 한국어·원화·월요일 시작이 하드코딩입니다.
- **CSS 전역 충돌 위험.** 컴포넌트마다 `<style>` 태그를 렌더링하며, 클래스명이 `.chip`, `.day-row`처럼 매우 일반적입니다. 모달을 열 때마다 스타일이 재삽입됩니다.
- **죽은 코드.** `sha256`, `loadAuth/saveAuth/clearAuth`, `STORE_KEY` 등 Firebase 이전 PIN 시절 잔재가 남아 있습니다.
- **`firestore.rules`가 레포에 없습니다.** 서비스의 보안 경계 전체가 버전 관리 밖에 있습니다.

## 4. 골격 제안 — 하나의 타임라인, 세 개의 렌즈

### 지금의 문제

컨셉은 "같은 캘린더 축에서 3가지를 관리한다"인데, 구현은 **3개의 독립 캘린더를 탭으로 묶은 것**입니다.

- 탭을 바꾸지 않으면 오늘 할 일과 오늘 나갈 돈을 같이 볼 수 없습니다.
- 아이디어를 할 일로 승격하는 경로가 없습니다. 축 간 이동이 없으니 축이 3개인 이유가 약합니다.
- **가계부가 목적을 수행하지 않습니다.** CLAUDE.md는 "미래 현금 흐름 파악"이 목적이라 적었는데,
  잔고는 수동 입력 숫자 하나이고 예정 입출금은 캘린더에 흩어진 항목일 뿐,
  **둘을 합쳐 "이 달 말 예상 잔고"를 계산하는 코드가 없습니다.**
  `MONEY_TYPES`를 7종으로 정교하게 나눠놨는데 집계가 없어서 그 분류가 쓰이지 않습니다.

### 제안

**하나의 `entry` 모델 + `kind` 필드. 탭은 렌즈(필터 프리셋)로 재정의. 네 번째 렌즈 "오늘/전체"를 추가.**

1. **통합 렌즈 (신규)** — 오늘·이번 주를 한 화면에. 할 일 3건, 떠오른 아이디어 1건, 나갈 돈 2건이 같은 날짜 줄 위에 얹힙니다. 이게 이 서비스의 첫인상이 되어야 합니다.
2. **축 간 전환** — 아이디어 → 할 일 승격 (한 번의 탭). 할 일 ↔ 지출 연결 (예: "노트북 구매" 할 일에 지출 200만 원을 연결하면 그 지출이 현금흐름에 자동 반영).
3. **현금흐름 예측** — 잔고 + 기간 내 예정 입출금 누적 = **일별 예상 잔고 라인**. 가계부 렌즈 상단에 이 한 줄만 있어도 7종 분류가 비로소 의미를 갖습니다. "언제 잔고가 바닥나는가"가 이 서비스가 답할 수 있는 유일무이한 질문입니다.
4. **기존 3탭은 그대로 유지.** 렌즈로 재정의될 뿐 사용자가 잃는 것은 없습니다.

### 왜 이 방향인가

투두이스트·노션·뱅크샐러드를 각각 이기려 하면 이길 수 없습니다.
그러나 **"할 일과 아이디어와 돈이 같은 날짜 위에 얹히는" 제품은 시장에 거의 없습니다.**
차별점은 기능 수가 아니라 세 축이 하나의 타임라인을 공유한다는 사실 자체이고,
그건 지금 구조에서는 구현되어 있지 않습니다. 골격 수정의 정당성은 여기에 있습니다.

CLAUDE.md의 "기능 추가보다 제거를 우선한다"는 원칙과도 충돌하지 않습니다.
탭 3개를 유지한 채 화면을 더 만드는 게 아니라, **3개를 하나의 모델로 합치는 축소**이기 때문입니다.

## 5. 데이터 모델 재설계안

```
users/{uid}                      프로필: displayName, locale, tz, currency, weekStart, plan
users/{uid}/entries/{id}         일정·아이디어·지출 통합
users/{uid}/accounts/{id}        잔고 (계좌 단위, 스냅샷 히스토리 포함)
users/{uid}/debts/{id}           대출 1건 = 1문서
users/{uid}/pins/{id}            고정 메모
```

`entry` 스키마:

```ts
{
  id: string
  kind: 'task' | 'idea' | 'money'
  title: string
  note: string
  color: ColorId
  tags: string[]

  startDate: 'YYYY-MM-DD'
  startTime: 'HH:mm' | null
  endDate:   'YYYY-MM-DD' | null
  endTime:   'HH:mm' | null
  ym:        'YYYY-MM'            // 월 범위 쿼리 키 (F-06 해결)

  task?:  { status, important, urgent, order, rrule }   // rrule: RFC 5545 부분집합
  money?: { type, amountMinor, currency, linkedEntryId }

  createdAt / updatedAt: serverTimestamp
}
```

핵심 변경:

- **`::balance::` 우회 제거.** `firestore.rules`를 레포에 두고 `accounts`·`debts` 컬렉션의 필드를 명시적으로 허용합니다. 에뮬레이터로 규칙을 테스트하면 "조용히 거부"가 사라집니다.
- **대출 1건 = 1문서.** 다중 기기 덮어쓰기(F-05)가 해결됩니다.
- **`ym` 인덱스 키.** 월 범위 쿼리로 F-06을 해결하고 과금을 사용량에 비례시킵니다.
- **금액은 최소 단위 정수(`amountMinor`).** 부동소수 오차를 원천 차단하고 다통화 확장 여지를 둡니다.
- **`rrule` 도입.** F-04(죽은 반복 기능)를 실제 전개 로직과 함께 구현합니다.
- **`kind` 통합.** 아이디어 → 할 일 승격이 필드 하나 변경이 됩니다.

기존 데이터는 일회성 마이그레이션 스크립트로 옮깁니다 (`items` → `entries` + `accounts` + `debts` + `pins`).

## 6. 기술 스택 결정

| 결정 | 선택 | 근거 |

### Supabase에 대하여

MIGRATION.md의 결론(지금 이관하지 않는다)에 동의합니다. 근거는 다르게 정리합니다.

- **찬성 논거는 실재합니다.** Postgres의 관계형 집계는 현금흐름 계산에 유리하고, RLS는 Firestore 규칙보다 표현력이 좋으며, 소셜 로그인이 내장되어 있습니다.
- **그럼에도 지금은 아닙니다.** 스키마 재설계(5장)만으로 현재 문제의 대부분이 해결되고, 백엔드 이관을 동시에 얹으면 "저장이 안 되는데 원인이 규칙인지 스키마인지 이관인지" 판별이 불가능해집니다.
- **재검토 시점**: 사용자가 붙고 나서 (a) 가계부 집계가 클라이언트 계산으로 감당이 안 되거나 (b) Firestore 읽기 과금이 매출을 압박할 때. 그때는 `entries` 스키마가 이미 관계형에 가깝게 정리되어 있어 이관 비용이 지금보다 낮습니다.

## 7. 단계 계획

### Phase 0 — 이관 + 결함 정리
Vite + TypeScript 전환 (MIGRATION.md 3단계), F-01 · F-02 · F-03 · F-04 · F-10 수정,
`tweaks-panel.jsx` 제거, 죽은 코드 정리, `firestore.rules` 레포 편입,
GitHub Actions(빌드 + 테스트), Cloudflare Pages 연결, Firebase config 환경변수화.
**끝나는 지점: push하면 자동 배포되고, 지금 동작하는 모든 것이 그대로 동작하며, 안 되던 3가지가 되기 시작합니다.**

### Phase 1 — 데이터 모델 재설계
`entries` / `accounts` / `debts` / `pins` 분리, 마이그레이션 스크립트, 월 범위 쿼리,
오프라인 지속성 + 낙관적 업데이트, 보안 규칙 에뮬레이터 테스트. (F-05 · F-06 · F-08)

### Phase 2 — 골격 변경 ★
통합 렌즈(오늘/전체), 축 간 전환(아이디어→할 일, 할 일↔지출 연결),
**현금흐름 예측 라인**, `rrule` 반복 전개. (4장 전체)

### Phase 3 — 상용화 필수
비밀번호 재설정 · 이메일 인증 · 소셜 로그인, 계정 삭제 · 데이터 내보내기,
이용약관 · 개인정보처리방침, 랜딩 · 온보딩, PWA(설치 + 오프라인), 에러 추적.

### Phase 4 — 수익화
무료/유료 경계 설계, 결제 연동, 사용량 계측.

## 8. 시작 전 확인이 필요한 사항

1. **현재 Firestore에 살아있는 실데이터가 있습니까?** 있으면 마이그레이션 스크립트가 Phase 1의 필수 산출물이 되고, 없으면 스키마를 파괴적으로 바꿔도 됩니다.
2. **`firestore.rules`의 현재 내용을 받을 수 있습니까?** Firebase 콘솔 → Firestore → 규칙 탭의 텍스트입니다. `::balance::` 우회를 걷어내려면 지금 무엇이 막고 있는지 확인해야 합니다.
3. **이번 작업의 도달 지점**: Phase 0까지 / Phase 1까지 / Phase 2까지.
